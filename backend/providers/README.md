# Production provider boundary — not configured

No production WhatsApp adapter is included or enabled in this release. No pairing codes, credentials, group joins or real broadcasts are generated by the web app.

A future operator-reviewed adapter must implement `DeliveryProvider` from `backend/dispatch.ts`. It must:

- use a permitted, consent-based messaging approach and be reviewed against current provider/platform policies; an unofficial library is not equivalent to platform approval;
- register only provider-authenticated account identifiers with `recordProviderPairing`, keeping a persistent secret HMAC key; possession of a number does not prove group advertising consent;
- encrypt/isolate session credentials, revoke them on unlink, avoid exposing raw number identifiers or credentials to logs/browser clients, and define key backup/rotation/retention;
- refresh current membership and posting permissions before every send; consent evidence must be independently verified from a current group administrator;
- supply a provider-generated stable message ID before sending, and never use HTTP 200 or server acceptance as delivery proof;
- authenticate and bind actual delivery receipts to the group and provider message ID; group delivery does not imply every member read the message;
- durably retain/replay confirmed receipts until the subscription callback resolves `true`; `false` means settlement failed and the event must remain pending;
- reconcile `UNKNOWN` results without blindly resending. No automatic group joining, anti-ban evasion or automatic group leaving is implemented.

Setting environment variables cannot create this integration. `npm run worker` refuses to start without an installed, ready adapter. The production release script does not start Redis or the worker. The BullMQ pipeline is exercised with an explicitly synthetic provider only in isolated automated tests.
