# Plogme personal-broadcast pilot — v0.3.0

**Historical v0.3.0 record. Current behavior is documented in `POSTING-PACING-MEDIA-0.10.0.md`, `MOBILE-POLISH-0.9.0.md` and `WORKER-EXPERIENCE-0.8.0.md`.** In current code, PAPPYPAY is the actual custom pairing code, native personal posting has no extra approval-command prerequisite, posting quotas have been removed, and group pacing is configurable. Historical implementation/limits below must not be reintroduced as current requirements.

## Implemented
- Exact Plogme 2.1.0 integration, two owner-bound linked-device slots, real provider identity validation, actual group scans and membership/admin/lock updates. No pairing or broadcast is simulated.
- PAPPYPAY-branded pairing card with unique private eight-character codes and copy controls. Codes are deliberately not the publicly reusable literal PAPPYPAY. The provider must supply a code, and confirm the matching phone before an account is marked online.
- AES-256-GCM credential/Signal-key/code storage with per-entry AAD and nonces. Persistent encryption and identity-HMAC secrets remain outside the database/image/Git.
- Owner-authenticated APIs, existing same-origin/custom-header/CSRF requirements, worker-role checks, per-owner pairing limits, a narrowly scoped raw-media upload exception. No public settlement or funding endpoint.
- Scoped group-admin approval: status, chat and mention-all separately. Current owner-admin authority is rechecked; otherwise a real current admin sends the expiring command in the exact group. Approval lasts 30 days unless revoked. No command is automatically posted and no group is automatically joined.
- Durable personal `allstatus` (actual group-status flag), `allchat` (group-chat payload with authorised mention-all), and `2x` (status submitted first, then chat) queues. Shared groups are deduplicated. Fresh membership/permissions checked immediately before send. Provider acceptance is labelled **Submitted / delivery unverified**, not confirmed delivery or views. Unknown sends are never blindly retried.
- Provider removal creates an owner/group block and revokes both numbers' scopes. Rejoining, rescanning, switching slots or the legacy paid reservation path cannot bypass it. Fresh verified group-admin permission is required; the existing paid campaign/group claim still prevents reposting the same campaign.
- Personal runs have immutable purpose/payload/targets/rewards, zero earnings, zero referral qualification, zero bonus progress, and do not use the ten paid-campaign participation slots.
- HTTPS/public-IP DNS-pinned preview fetches, redirect validation, TLS validation, body/time limits, metadata only; no remote thumbnails. Every message has a visible link. Required-preview mode fails closed; media captions do not promise a separate preview card.
- Private image normalisation/metadata stripping, H.264/yuv420p MP4 validation (AAC audio if present), GIF-to-MP4 conversion using ffprobe/ffmpeg. Saved-media reuse/removal controls. Unsupported audio/documents/stickers are explicitly rejected, not silently dropped.
- Independent internal funded-placement accounting: exact integer milli-Coins, `min(members,1000)` per confirmed surface, 100-member minimum, no 100-group earning ceiling, ten distinct paid campaigns/day, independently preserved partial 2x earnings, treasury/referral/bonus backing and cross-path claims/reconciliation.
- Attribution and full upstream licence are retained in `docs/LICENSE-PLOGME.txt`, the installed package and public `#/plogme-license`. Do not claim that knowing the author itself supplies written commercial permission.

## Resource limits — not reward changes
Personal beta: three runs per UTC day, at least 60 seconds apart, up to 200 selected memberships/run before deduplication. These limits are shown in the composer and do not cap paid group earnings. Media: 8 MiB input/file, 50 MiB and 100 stored files per owner, 512 MiB stored server-wide, at most two concurrent conversions and one per owner. Images: at most 16 MP input / 2048px output. Video/GIF: at most 90 seconds / 1920px; CPU/time bounded. GIFs become MP4, not a promise of native animated-GIF looping. Manual joining is recommended; no autojoin/invite scraping exists.

## Not verified or enabled
No real WhatsApp pairing, message, group status, mention-all notification, preview rendering or group join has been performed by the assistant. Actual device compatibility, especially group-status/media support and receipt behaviour, needs owner testing. Library/provider restrictions or account disconnection are possible; WhatsApp/Meta endorsement is not claimed.

The new paid accounting kernel is tested with explicitly synthetic provider evidence. **There is no live paid Plogme dispatcher/receipt verifier or automatic paid campaign allocator.** `beginPaidPlacement` refuses unverified receipt capabilities. No public endpoint manufactures confirmations. Paid dispatch, queue worker, checkout deposits, withdrawals and payouts remain OFF; real funding remains zero. Provider acceptance alone never earns money. Pricing-table and provider-approval questions remain unresolved. This is not a claim of a complete commercial platform, PostgreSQL migration or universal payload support.

## Deployment and operations
`WHATSAPP_ENABLED=true` enables personal owner-testing, not paid earning. The release script provisions root-only `/etc/pappy-earning-hub/whatsapp.env` once with two independent 32-byte secrets and reuses it across releases. Never print, commit or rotate these during an ordinary release. Without those exact keys, saved sessions/phone ownership history cannot be recovered correctly. Keep a separate secure encrypted offline backup of this file; SQLite backups alone are insufficient.

SQLite and private media live in the existing persistent data volume (`/app/data`, host `/var/lib/pappy-earning-hub`). Existing backup command verifies a SQLite snapshot, including encrypted auth; it does not copy media or secret keys. Back up media separately. Periodically remove old unreferenced files left by interrupted uploads (no automatic destructive sweeping). Do not delete media used by queued/running work. Owner deletion keeps a zero-byte metadata tombstone for immutable history.

Docker installs ffmpeg and pinned npm dependencies with install hooks disabled; Sharp and Plogme import/native execution are checked separately. Existing container isolation/read-only root/limits remain. Release builds before stopping the previous app, creates a verified SQLite backup, preserves the prior container and restores it if startup fails. Migration 3 only adds compatible tables/indexes/triggers; no original accounts, wallet balances or cash are manufactured. A container rollback leaves the additive schema in place.

Use Connections to pair an owned number, scan its real groups, then Personal broadcasts to request permission, choose content/link/media and explicitly queue a run. Keep an initial test to one group whose admins consent. Never supply a WhatsApp registration OTP or two-step PIN to the app. Unlinking deletes local credentials; if remote logout cannot be confirmed, remove the device from WhatsApp → Linked devices manually.
