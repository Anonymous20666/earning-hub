# v0.5.0 — personal all-group composer and real posting console

## Flow
Text / Media → write text, paste a link with attached text, or upload an image/video → optionally add multiple ignored-group invite links → review the immutable server draft and automatic group check → explicitly confirm → post to every eligible unique owned group. No group picker. Plain text and media without a link are now supported for personal posts; paid-campaign destination rules are unchanged.

A review refreshes participating-group inventory for the owner's online numbers. Targets require actual owner membership, a connected number, no owner exclusion/removal block, and unexpired group-admin permission for the requested surfaces (including mention-all for chat). Shared groups across two numbers are deduplicated, preferring an eligible membership. Below-100-member groups are included. Ignore links are looked up using `groupGetInviteInfo` only, never joined; an invite must resolve to a group already in the owner's current inventory. A batch is saved atomically only after all links resolve. The database stores group IDs/names and invite-code hashes, not raw invite links. Lists are owner-scoped and may be edited. New ignore entries also prevent not-yet-started queued sends.

Review drafts last ten minutes, are tied to the owner and payload, and detect target/permission/ignore changes at confirmation. Confirmation has a stable request key; duplicate clicks/retries/reload cannot create another run. Large duplicate draft content is cleared on consumption; the immutable run retains its payload. The same permission, membership, connection and removal checks are repeated immediately before each actual send. Existing personal beta limits remain **3 runs per UTC day, 60 seconds between runs, 200 eligible unique groups per run**. More than 200 eligible groups is an explicit error, not silent truncation. This is not a new limit on paid earnings.

## Native link previews and colourful statuses
Adapted the user-authorised private `saas-spam` branch `shard/state-plane` patterns, rather than importing/executing its application or downgrading dependencies:
- Extract OG/Twitter/HTML title and description. Add the real title without dropping the original multiline text/link. Preserve the exact matched URL and avoid duplicate canonical-slash links.
- Fetch only public HTTPS resources with public-address checks, DNS pinning and revalidation on every redirect. Shared 12-second fetch budget; up to three redirects; first 256 KiB HTML head data; images up to 2 MiB; strict raster MIME and byte-signature checks before Sharp; 16-megapixel decode bound. SVG/mislabeled files, tracking pixels and private image destinations cannot become previews.
- Real raster image only, JPEG-normalised with orientation/aspect ratio preserved and no crop. Useful small images are proportionally enlarged; large/complex images are compacted. Separate bounded HQ JPEG and compact inline JPEG. No invented image/banner or false video/playback metadata.
- During an explicitly authorised send, upload the real image with SDK `prepareWAMessageMedia`, the active socket upload function, `mediaTypeOverride: thumbnail-link`, and a 15-second media-upload timeout. Supply inline `jpegThumbnail`, uploaded `highQualityThumbnail`, actual dimensions and static-image `previewType: 5`; no image means type 0. Uploaded metadata caches are socket-scoped, capped and expire after five minutes; session shutdown drops them. Upload failure keeps the real inline JPEG, not a fabricated substitute.
- Rotate readable dark status colours per text-status placement and between runs. Set colour/font in both content and send options, as the installed Plogme SDK requires. Media captions stay with their uploaded media; a separate native link-preview card inside a media caption is not promised.

Some websites block automated metadata requests or supply no usable image/title. Those posts keep the original text/link instead of manufacturing a successful preview. Actual WhatsApp client rendering is not guaranteed by encoding tests and still needs owner validation.

## Console truth and reliability
The console polls a private, owner-authorised cursor feed of durable SQLite events: queued, skipped (with reason), checking, attempting, SDK-accepted, failed, uncertain and finished. Timestamps are server-recorded ISO times; the visible clock is synchronised from server responses and explicitly labelled Lagos / UTC+1. No fake timed progress or invented posting events. Includes current/last group, actual attempt count, follow/pause scrolling, stop-unsent control, separate accepted/skipped/failed/uncertain totals and final completion feedback. Reload reopens recent activity without posting again.

“Sent to WhatsApp” means the SDK accepted the exact persisted message ID, **not confirmed delivery, reading or views**. Started sends that time out/restart/fail ambiguously become UNKNOWN, never blindly retried. In 2x mode status goes first; an uncertain or failed status cancels that group's pending chat rather than stranding the run or silently proceeding. Restart recovery records uncertainty and safely closes blocked runs. Cancellation and its log are atomic/idempotent; finished history is not relabelled cancelled.
